# Architecture research: where WARP can be different

**Date:** 2026-09-28 · **Purpose:** research synthesis to guide the reopened architecture exploration. This document records hypotheses, not a selected design.

## Competition target

The current Jane Street brief explicitly asks for an open-source, general-purpose protocol emulator, says fixed UART/SPI/I2C blocks are not the goal, and asks entrants to show other things their architecture enables. It also names unique functionality and novel design/verification methods as judging interests. The current limit is 6 × 4; 8 × 4 remains unconfirmed. Therefore WARP should optimize for **useful new behaviors per fixed area** and provide direct evidence of what its spatial eFPGA enables. Raw counts of protocol bitstreams are weak evidence if they run only one at a time.

## Architecture landscape

### Established programmable-I/O structures

The RP2040 is instructive for resource sharing: each PIO block has four independent state machines, but the state machines in a block share a small instruction memory. Each retains its own shift state, scratch state, divider, and FIFOs. That amortizes code storage when the same program runs on several pins. The RP2040's official SDK describes the per-machine shift registers, FIFOs, fractional divider, flexible GPIO mapping, and DMA pacing ([Pico SDK PIO hardware documentation](https://www.raspberrypi.com/documentation/pico-sdk/hardware.html)). NXP FlexIO independently demonstrates composition from generic shifters, timers, and pins for UART, SPI, I2C, I2S, displays and PWM ([NXP FlexIO overview](https://www.nxp.com/design/design-center/software/development-software/mcuxpresso-software-and-tools-/specialized-peripherals-for-nxp-microcontrollers%3ASPECIALIZED-PERIPHERALS-MICROCONTROLLERS)).

**WARP implication:** the earlier sequencer area model's per-lane program memories are an avoidable cost when multiple endpoints can run the same code. A temporary synthesis probe shows sharing an 8-word, 24-bit instruction image between two independently advancing lanes reduces mapped area from 42,553 to 30,054 µm² (about 29%); a 16-word image saves about 35%. It keeps a separate PC and data/timer/pin state per lane and needs two instruction read ports. These numbers come from an intentionally incomplete RTL cost probe, without a physically built SRAM or correct protocol timing semantics, so they only establish that shared code memory deserves a proper experiment. The exact results and limitations are in [`architecture_screen.md`](architecture_screen.md).

### Current competition entries

Public project pages describe a rapidly converging design space:

- **Tempo** reports a complete two-engine instruction-based emulator, 64 × 24-bit writable program memory per engine, deadline/timing controls, four-entry data queues, pin ownership, contention diagnostics and timestamp capture. Its README also reports physical and gate-level verification; these are the authors' own results, not an independent reproduction ([Tempo README](https://github.com/satyaammu93/jane-street-asic-2026/blob/main/protocol_emulator/README.md)).
- **BitLoom** describes multiple PIO-style machines with deadline timing, capture and protocol examples ([BitLoom repository](https://github.com/sheehanmunim/bitloom)). Its reported feature set is self-published.
- **Abagel's proposal** describes a time-triggered CPU plus two programmable line-coding lanes, CRC/stuffing, timestamp FIFOs, pin contention monitoring and formal timing/liveness claims. The repository currently labels the architecture as a proposal and lists only a UART transmitter warm-up with three local checks. Its 7–8K-cell block budgets are explicitly estimates, not measured results ([proposal](https://github.com/Abagel-coder/protocol-emulator/blob/main/docs/superpowers/specs/2026-09-15-protocol-emulator-design.md), [project status](https://github.com/Abagel-coder/protocol-emulator)).

**WARP implication:** “two independent lanes,” “absolute deadlines,” “capture,” “generic CRC,” or “formal timing” alone are no longer good differentiators. WARP's credible potential advantage is **spatial programmability coupled directly to temporal I/O**: user-synthesized logic can observe, transform, coordinate and react to generic event streams in parallel with pin engines. That advantage is currently a hypothesis. The showcase should prove one simultaneous example that is difficult for a small sequential core, such as one link emulator reacting to a second live monitor while the LUT fabric applies a user-defined filter/trigger or packet transform.

### PRISM is the closest hardware prior art

The TinyTapeout PRISM project page describes a 5 × 4 SRAM-less design and a larger 8 × 4 build. Its programmable state machine has 32 128-bit state words, or two independent 16-state shards. Each shard has six input selectors over 32 signals, conditional transitions, and 21 outputs. The fixed datapath already includes counters, an 8-bit communication shifter, constants, FIFOs, configurable CRC-8/16/32, a Manchester recoverer, edge-triggered sampling, edge capture, a timer, interrupts and debug support; the larger configuration adds SRAM FIFOs and trace storage. The Verilog Mealy machines are compiled into the state table. The project page lists UART, SPI master/slave, I2C master/slave, 1-Wire, WS2812, USB low-speed and 10BASE-T examples, with the Ethernet/SRAM features tied to the larger configuration. These are PRISM's project-reported results; the page says its protocol suite runs against a gate-level netlist, and none of the area or coverage was independently reproduced for this report ([TinyTapeout PRISM design page](https://tinytapeout.com/chips/ttihp26b/tt_um_pettit_prism_lite)).

This changes how WARP should evaluate event-lane hardware. Two lanes, shared code, a loaded instruction/state table, shift/timer primitives, CRC, capture, and protocol coverage are all weak novelty claims by themselves. The event-lane spike is useful as an area/interface probe, but it is not the architecture to pitch. The differentiating hypothesis must be the **user-programmable spatial fabric acting as a live data-path partner**: for example, a Verilog-defined transform or classifier consumes bytes from one timed lane and drives a response through another while a separate monitor runs. If the hybrid cannot demonstrate that connection at equal whole-chip area, WARP should invest in a better spatial fabric rather than add a PIO-like engine.

The public **ProtocolGremlin** repository now describes a CPU-style 24-opcode pin engine with edge waits, shift operations, open-drain support and a large protocol-program catalogue. Its claims of protocol counts and area are repository-reported and have not been independently reproduced ([ProtocolGremlin README](https://github.com/Vedant817/ProtocolGremlin)). This further raises the bar for any generic sequencer proposal. The **GP_PAE** README also describes multiple independently running sequencer lanes with writable code memory, UART/SPI/I2C examples and a multi-check verification flow; its reported core area is generic synthesis rather than a PDK-mapped placed result ([GP_PAE README](https://github.com/sjrai007/gp_pae)).

### eFPGA optimization findings

The most directly applicable result is the FABulous-specific tile optimization study by Chung, Dao, Yu and Koch. It combines configuration-cell placement remapping with tile-interface pin remapping and reports 21.7% area reduction and a 6.1% worst tile latency improvement for its optimized LUT4 CLB. Its physical experiments used SkyWater 130 nm and Cadence Innovus, not IHP CMOS5L and OpenROAD, so the percentages cannot be carried over to WARP ([accepted manuscript](https://pure.manchester.ac.uk/ws/portalfiles/portal/207833524/FPGA_2020_FABulous_optimizations_1_.pdf), [publication record](https://research.manchester.ac.uk/en/publications/how-to-shrink-my-fpgas-optimizing-tile-interfaces-and-the-configu/)).

The same study found that straightening configuration cell placement and choosing tile border pin locations can reduce congestion. It also found frame-based configuration more area-efficient than a conventional shift-register configuration in the studied fabrics. WARP already uses frame-based latches, so a configuration architecture switch to scan/shift chains has poor evidence and should not be a leading candidate. The project’s own G1 tile has 74.2% of configuration bits assigned to switch-matrix choices; that supports studying physical configuration and routing layout, but not assuming equivalent area is recoverable.

The installed FABulous 2.2.0 Python package contains a tile-area optimization flow with `find_min_width`, `find_min_height`, `balance`, and `large` modes, along with a configurable tile-pin placement step. WARP's current CMOS5L spike runner does not call that loop: it uses a fixed size table in the copied `fabulous-tiles/tiles.py` and the generated G1 `ConfigMem.csv` maps feature bits in regular sequential ranges. That gives a concrete route to test the literature: run the supported optimizer from a scratch copy of the WARP LUT tile, with width fixed/minimized under the 199.08 µm row-height ceiling, and compare the optimized feature-bit mapping and border-pin assignment with the current file. The local tile runner's Nix-pinned FABulous plugin predates this API, so the first gate is proving a reproducible flow with the pinned tools before trusting any dimensions.

A classic FPGA architecture paper by DeHon argues that interconnect can dominate programmable-array cost and that maximum LUT utilization is not always the best area point. This supports measuring the routing graph and physical metal pressure together with logic capacity ([Berkeley author-hosted paper](https://brass.cs.berkeley.edu/documents/fixedws_fpga99.pdf)). The newer eFPGA study on custom mux/configuration cells reports gains at 28 nm and likewise emphasizes congestion-aware wiring; that result is useful motivation, not a CMOS5L estimate ([study DOI](https://doi.org/10.1016/j.mejo.2024.106544)). OpenFPGA's published architecture language provides another reference for exploring LUT fracturing, switch topologies, config memory and hard blocks as separable knobs ([OpenFPGA paper](https://woset-workshop.github.io/PDFs/2020/a19.pdf)).

## New candidate: recover a fifth logic column

WARP's measured 4 × 3 fabric is about 1016.64 µm wide and leaves roughly 272.64 µm for the shell column. A 5 × 3 grid at current tile pitch consumes about 1236.48 µm and leaves only 52.8 µm, below the project's 200 µm shell estimate. At fixed die width, preserving the edge tiles and the shell estimate requires the interior tile pitch to fall from 219.84 to at most 190.4 µm. The available die height permits a taller interior tile, up to about 199.08 µm. This gives a test geometry of approximately 190.4 × 199.08 µm per logic tile, against the current 219.84 × 185.22 µm tile.

A 5 × 3 grid could hold 112 LUT4s and the measured 2+2 primitive tile if one slot is reserved, or 104 LUT4s with two primitive slots. The former adds 24 soft LUTs at unchanged timer/shifter capacity relative to G1; the latter adds 16 LUTs and doubles those generic timing/data resources. It may make dual-link concurrency credible. The target slot's area is about 37,903 µm², near the existing LUT tile's 36,047 µm² standard-cell area before repair cells, filler, routing and boundary infrastructure. The two-primitive option is especially tight. This is a physical feasibility experiment, not an architectural conclusion.

**First CMOS5L feasibility result (2026-09-28):** the pinned tile runner was run in an ignored build copy with the LUT tile's die dimensions changed to 190.40 × 199.08 µm; no tracked architecture files were changed. The flow generated the tile and reached OpenROAD global placement, which stopped with `GPL-0301: Utilization 106.507% exceeds 100%`. The run reports 35,943.264 µm² movable cell area, a 1,160.105 µm² pin-density adjustment, and 34,836.480 µm² core area. Even if pin remapping eliminated the entire pin-density adjustment, movable cell area alone would still be 3.18% above core capacity; with the current pin adjustment, at least 6.11% of placed footprint must be recovered just to reach 100%, before allowing placement/routing margin. Thus this is not solvable by pin reordering alone; a useful optimization must also reduce cell area or repair/buffer overhead. No detailed route, DRC, timing or GDS was produced. Reproduce with `spikes/tile_cmos5l/run.sh LUT4x8_ha` after setting the `ihp-sg13cmos5l` entry for `LUT4x8_ha` in the ignored `build/tile_cmos5l/fabulous-tiles/tiles.py` to `(190.40, 199.08)`; `build/tile_cmos5l/LUT4x8_ha.log` contains the placement failure. Do not infer a 5 × 3 fabric fit from this tile-only attempt.

**Route-option pruning result (2026-09-28; corrected and regenerated):** the initial software comparison used a stale nominal-corner PIPs file, and the first full-fabric model also used stale tile artifacts. I rebuilt the clock-protected 5 × 3 software model from the exact hardened tile source: candidate tile RTL declares 530 configuration bits, its generated configuration map covers bits 0–529, and the regenerated feature map/router model use the same tile definition. On this consistent model, UART, SPI controller, and I2C controller each place/route and generate bitstreams; independent FASM-to-word reproduction and 5-row frame checks pass (842 words per image). The clock-protected manifest restores six global clock/reset/enable PIPs and removes 307 of 1,272 local switch choices per LUT tile (24.1%). The earlier 4 × 3 and aggressive 5 × 3 routeability claims remain unverified against fully regenerated tile RTL/configuration data. The I2C target is not a useful comparison because it exceeds the 88-LC fabric's logic capacity. Candidate nextpnr timing PIPs use placeholder delays, so its reported Fmax values are meaningless. Direct RTL loading reaches host-ready and emits a UART start bit when reset is held through configuration. The first payload check failed because its testbench began waiting for `negedge tx` after the valid/ready handshake and missed the start edge. Re-arming the observer before valid, then checking the start bit, all eight data bits and stop bit, passes for 0x96 LSB-first. A generated scratch seven-column shell wrapper around the existing `wp_shell`, loader and candidate macro passes UART: candidate WBIT load over host SPI, RUN, CH_WRITE 0x96, and one valid 8N1 frame at FAB_OUT0. SPI controller mode 0 also passes against the reference target; the I2C controller passes open-drain register write/read and unknown-address NACK checks; `hostecho` passes CH_WRITE/CH_READ, USER_STATUS, attention/IRQ, and USER_RESET. The candidate inout shell wiring was exercised by the I2C test. These are RTL simulations using design-set workloads, not physical shell signoff or full-macro hardening.

**Partial candidate PIP characterization (2026-09-28):** the first probe used a stale 375-bit aggressive tile snapshot and was discarded. The corrected run used the 378-bit clock-protected `RUN_2026-09-28_20-53-31` final RTL, netlist and extracted nominal SPEF at the IHP slow corner; its switch-matrix RTL SHA256 matches both the current tile source and candidate macro copy. A temporary adapter was needed because the installed FABulous synthesis helper emits a Tcl-interactive Yosys script that the installed Yosys does not accept as written. Of 864 internal LUT-tile PIPs, 862 produced physical delays from 0.001 to 6.089 ns (median 0.766 ns, p95 2.597 ns); two arcs into `J2END_GH_BEG3` failed because `N2END[1]` and the mux fanout are absent from the physical timing graph. The root cause is that the clock-protected manifest removes both downstream connections from `J2END_GH_END3` to `LG_I3` and `LH_I3`, leaving the mux as an orphan that synthesis removes. These two source arcs are therefore retained but unusable dead-end choices in this manifest; the manifest should be regenerated without them and route-checked before claiming a cleanup. The model returned all 202 external LUT-tile PIPs, though 198 use its fixed 0.001 ns stitched-wire assumption and four global-buffer twists use extracted tile delays of 0.085–0.091 ns; these are not extracted inter-tile wire delays. Raw rows are under ignored `build/arch_explore/route_prune/timing/`. This is useful partial tile-level characterization, but does not cover other tile classes or all BEL arcs. Candidate Fmax remains invalid.

**Orphan-lane cleanup probe (2026-09-29):** deleting the two source PIPs alone is rejected by FABulous because the four-wire `J2END_GH` lane is still declared. A disposable 5 × 3 candidate instead gives only the LUT tile a three-wire `J2END_GH` base definition, removes lane 3's mux choices, and regenerates tile RTL, config map, fabric RTL, PIPs and bitstream spec. The LUT tile config width drops from 530 to 529 bits. UART, SPI-controller and I2C-controller all rerouted successfully with nextpnr; each resulting FASM compiled to 842 words. An end-to-end configured-fabric RTL simulation loaded the UART bitstream through `wp_fabric_cfg` and transmitted `0x96` LSB-first with valid start/stop bits. Routes differ from the 530-bit candidate because the routing graph changed.

For physical screening, a clean-tree run using the current FABulous 2.2 tile optimization flow expanded both the candidate and 530-bit baseline beyond the requested 190.4 × 199.08 µm target to pin-driven minimum bounds (candidate 256.19 × 274.91 µm; baseline 256.34 × 275.06 µm). Both failed global routing. Candidate overflow was 217 with 164,577 µm wirelength; baseline overflow was 219 with 161,884 µm. This is near-neutral overflow and slightly longer wiring, not a demonstrated improvement. The current flow did not reproduce the previous baseline's 190.4 × 199.08 µm hardening run, so this result cannot replace that signoff or establish candidate fit. The tool environment needed temporary Nix Python wrappers for embedded Yosys and OpenROAD; all scratch artifacts remain ignored. The reusable manifest and shared G1 tile definitions are unchanged, and candidate Fmax remains invalid.

**Basic logic-path simulation (2026-09-28):** a scratch combinational `FAB_IN0` → `FAB_OUT0` design compiled and routed on this candidate, and its 842-word WBIT was loaded through `wp_fabric_cfg` into the generated macro RTL. The output followed input values 0 → 1 → 0. This validates a basic configured I/O/LUT path in simulation. By itself it does not validate UART or hard primitives; the subsequent candidate workload tests cover those RTL paths. It does not establish physical fabric timing or full-macro hardening.

For physical screening, both PPA candidates used the 190.40 × 199.08 µm LUT4x8_ha tile target. The aggressive tile synthesized to 29,824.2 µm² / 1,595 cells and reached 88.8% global-placement utilization; the unpruned baseline synthesized to 34,831.7 µm² / 1,825 cells and failed placement at 106.507%. The clock-protected tile synthesized to 29,820.5 µm² / 1,580 cells and reached 88.8% utilization. It completed the pinned LibreLane/OpenROAD/KLayout tile flow, with KLayout DRC clear. Run directories are `build/tile_cmos5l/fabulous-tiles/tiles/tiny/LUT4x8_ha/runs/RUN_2026-09-28_20-19-32/` (aggressive), `RUN_2026-09-28_20-53-31/` (clock-protected), and `RUN_2026-09-28_19-44-44/` (unpruned). The manifests and application script are in `spikes/route_prune/`. Keep G1 frozen: no held-out routes, full-fabric hardening, or physical shell result exists. The candidate has direct macro and scratch-shell RTL workload passes, but still needs realistic PIP delays and full-fabric/shell physical feasibility evidence. Its 5 × 3 pin map shifts I/O locations and requires seven configuration columns; the active shell still uses six. Promote it only after candidate-specific timing and physical checks pass.

This run also changes how to rank the event-lane spike. The proposed tile boundary has 29 routed inputs and 32 routed outputs. FABulous 2.2's documented `generate_custom_tile_config` path supports at most 32 internal inputs and 8 internal outputs per tile ([FABulous custom-tile guide](https://github.com/FPGA-Research/FABulous/blob/main/docs/source/user_guide/building_doc/fabric_automation.md#generating-a-custom-tile)). This is a limit of that supported generator path, not proof that the RTL/fabric format cannot express more. The event tile would need bespoke tile and switch-matrix generation plus compiler/bitstream changes; it should remain a lower-priority option until that path is demonstrated.

**Experiment:** use the newer FABulous tile-area optimization flow only if it can be made reproducible with the pinned CMOS5L tools; otherwise automate a bounded width/height sweep in scratch builds. Optimize LUT and primitive tile interfaces/configuration mapping; harden each candidate in the real CMOS5L flow; then generate a separate 5 × 3 fabric and prove the shell, pin routing, configuration frames and representative concurrent designs. A physical fit is useful only if the bitstream compiler and router can exploit the extra column.

## Architecture directions ranked for investigation

| Rank | Direction | Why it may matter | Required evidence / main risk |
|---:|---|---|---|
| 1 | **FABulous-specific tile and config remapping, with a 5 × 3 target** | Could recover 24 LUTs while improving the eFPGA itself; strongest directly applicable physical paper and protects WARP's spatial identity | Real tile hardening with CMOS5L layers, then fabric routing and full core fit. The target has little utilization slack. |
| 2 | **Communication-shaped spatial routing and I/O graph** | Improve the eFPGA's routing efficiency and parallel logic capacity without turning the architecture into another microcoded state machine | Must preserve the held training workload's route success; requires router and hardened-macro evidence. |
| 3 | **Hybrid event lane plus a user-logic streaming interface** | Could combine deterministic pin timing with arbitrary Verilog-defined spatial transforms, which is the clearest potential distinction from PRISM and CPU-lane designs | Must show a real lane-to-fabric handshake and concurrent transform at equal whole-chip area. Shared code and lane count alone are not differentiators; FIFO and interconnect costs may erase the density benefit. |
| 4 | **Generic event capture and trigger implemented in or beside the spatial fabric** | Could make WARP useful as a concurrently programmable protocol monitor/instrument | Capture itself is common prior art; prove custom LUT reactions and account for trace storage. |
| 5 | **Generic line-code/CRC assists** | Shared bit insertion/removal or programmable polynomial CRC could reduce cost for unrelated encoded links | Size and pin timing must be measured; PRISM and other entries already describe CRC/line-code support. |
| 6 | **LUT6 or fracturable LUT tiles** | Fewer LUTs for some controllers may improve logic capacity | LUT6 truth tables have 4× LUT4 configuration bits; harden area and route before further investment. |

The highest-confidence direction is **make the spatial fabric denser and better connected**. Keep the shared-image event-lane spike as a control. Advance a hybrid only after adding a backpressured stream interface and proving a user-defined fabric transform between independently timed pins. This is a hypothesis to evaluate against G1 and against published PRISM/PIO/CPU architectures, not a selected replacement.

## 5 × 3 physical stitch attempt (2026-09-29)

I launched the clock-protected 5 × 3 candidate through the pinned CMOS5L FABulous/LibreLane 3.0 fabric flow in an ignored build directory. FABulous successfully read the architecture and generated the bitstream specification, but the stitch stopped before floorplanning because the scratch tile library did not contain the hardened `PRIM2T2S.lef`. The LUT tile's physical views existed; the remaining tile types had no exported physical views in this candidate library.

To satisfy that prerequisite, I reran `PRIM2T2S` hardening in `build/tile_cmos5l/fabulous-tiles`; run `RUN_2026-09-29_12-08-16` synthesized 33,961.2 µm² of standard cells and reached the configured post-global-placement repair step. Repair inserted buffers, but detailed placement failed with `DPL-0036` on 1,259 instances. No LEF or GDS was produced, so the fabric stitch remains blocked. This repeats the physical constraint already recorded in D-031: repairing high-fanout primitive control nets does not fit the current tile footprint. It does not establish whether a redesigned primitive tile or a 5 × 3 fabric can fit.

All outputs are scratch build artifacts; the tracked architecture and G1 macro were not changed. The next useful physical experiment must reduce primitive control fanout/repair demand or revise the primitive resource mix and then produce physical views for every tile class before the full fabric flow can answer the area/congestion question.

## Evidence boundaries

1. The contest brief is dynamic; treat 6 × 4 as the target until its official page says otherwise.
2. Competitor pages state their own measurements. Distinguish implemented hardware/physical evidence from proposals and estimates.
3. Literature numbers use different processes, metal stacks and back-end tools. Use them to select experiments, then obtain WARP CMOS5L measurements.
4. Keep the fresh held-out protocol set sealed before any successor tuning, per D-037. Existing WS2812, 1-Wire, SWD and CAN results have already been opened.
5. No new behavior is supported until it maps, routes, survives full-chip hardening, loads from a bitstream and passes end-to-end tests.
